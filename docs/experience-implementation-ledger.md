# Experience implementation ledger: unpublished 1.15.0 candidate

Evidence date: 10 October 2026. The starting checkout was firmware 1.14.0 with substantial modified and untracked firmware, protocol and app work. Existing edits were preserved. No physical lamp, router configuration, saved credential, remote repository or store submission was changed. `docs/design` remains the design deliverable and historical snapshot, not a claim of shipped behavior.

## Current outcome and integration boundary

The implementation supplies negotiated device/model/effect contracts, revision-fenced partial controls and independent appearance memory, 32-position synchronized groups, confirmed group dissolution, stronger enrollment/household interfaces, exact-artifact update recovery/policy/signatures, and a local receiver progress animation. Existing authentication, catalog v1, settings/defaults, BLE/HTTPS updates, owner mesh and separate firmware donation remain available through their negotiated compatibility paths.

The update animation is an internal overlay, absent from both catalogs. It runs only on an actively installing receiver, using confirmed written bytes. Power and brightness are captured when the receiver is admitted; a lamp that started off remains dark throughout the operation. Checks, donors, other group members and postboot health alone do not show the cue. It does not save a mode, alter an individual's settings or broadcast a group effect.

The existing visual app was not replaced. Narrow model, endpoint, transport, credential, group-removal and transfer integration is implemented; the new UI still needs to consume the documented interfaces. All claims below separate source behavior, host verification, physical gates and further implementation.

## Storage and wire migrations

New endpoint numbers 40–52 extend the existing shared adapter; old paths/wire structures retain their contracts. BLE control wire version 1 retains its 1024-byte request/8192-byte response limit. New schema replies contain at most four entries/4096 bytes. Mesh admits explicit endpoint/method combinations, and private invitation result pages require confidential origin on every read. Complete `/api/state` includes one neighborhood hint with honest continuation; dedicated group status/pages contain eight. All 32 durable order identities remain in every group response.

Appearance items `coollamp/lookNN` use version 2 and 24 explicit bytes, including a twelve-byte canonical legacy baseline. Existing v1 color/options/audio records remain unchanged. Downgrade saves win on a changed baseline; upgrade rebases only changed existing items and exposes migration failures. Startup settings are not touched by dedicated saves. `updatePolicyV1` is a versioned 84-byte CRC record. Group protocol 3 has its own durable versioned configuration and follower slot; legacy group storage remains readable. Phone pending-removal records are versioned separately from owned inventory and never evict an owned card or another pending source silently.

Household records live in the user `coollamp` namespace and are cleared by user reset. Model metadata uses `lampmodel`; original publisher manifest, ratchet and the versioned CRC188-byte `otaAttemptV1` ledger use `lamptrust`. These survive user reset alongside existing physical settings. At most four unconfirmed exact artifacts are retained, without silent eviction; full/unreadable storage requires the documented repair/service route. Matching verified healthy installed data clears only that artifact, with failed clear retries limited to once per minute. A pending entry means unconfirmed boot selection/health, not proof that rollback occurred. Public trust roots are compiled material, not remotely editable user settings; this does not establish eFuse/Secure Boot protection. Reset interruption tests exercise the real reset handler and preservation boundaries.

BLE lease operations are additive, explicitly negotiated, and keep legacy disconnect-aborts semantics. Signed donation offers use a new body kind and preserve existing data/ACK/Finish wire layouts. Publisher enforcement rejects legacy unsigned routes where independent authenticity cannot be proven. No fallback silently bypasses an advertised enforced publisher policy.

python tools/test-experience-contracts.py
node --test mobile/tests/*.test.js

Native Windows GCC lacks ASan/UBSan; Linux CI retains both through `tests/host_compiler.py`. The release workflow now runs the contract gate before packaging; no workflow was dispatched here.

The broader baseline/final host sweep covers **111 distinct commands**, including existing effects/catalog, rising/falling/odd-count geometry, knob/audio, Wi-Fi recovery, Bluetooth, reset, protocol/radio/update runtime and tooling checks. Latest results are all passing in `.build/experience-final-host-summary.json`; historical fixture/integration failures and their passing reruns remain in the log. Hardware/device/USB checks were deliberately excluded. The final source-backed contract gate passes **23/23 commands**, including the new attempt guard. Mobile protocol/model/transport tests pass **610/610** and the production web build passes (48 modules). Native Android/iOS device and release builds are separate gates; a Vite build is not a store build.

Host group fixtures exercise actual thirty-one target subscriptions, driver cache limits, thirty-two positions, single-broadcast cadence, authenticated rejection/replay, durable offline order/pause, all scenes at 20/32 positions and mixed 1/3/205/1024 geometries. These are deterministic simulation results, not RF airtime or physical scale. Update suites include 31 actual BLE receiver scenarios, six radio handoff cases, 22 legacy and 27 signed donation scenarios, signature/retention/storage faults, recovery preflight, policy, cue and boot-health logic. Household tests execute real HMAC/NVS handlers and the native-client framing against exact signed responses.

## Physical and release gates

No requirement was physically verified in this implementation. Follow [the controlled acceptance and recovery procedure](experience-physical-acceptance.md): one independent canary first, preserve/compare settings, native iPhone and Android, actual three-node control handoff, signed/donor/interrupted updates, then mixed-style twenty-lamp streaming/removal/coexistence and staged rollout. Keep router configuration constant and pin exact digests. An actual installed rollback-capable bootloader/partition layout and a bounded faulty-image experiment must precede any automatic recovery promise.

Production signing/manufacturing/native identity material is an external prerequisite; autonomous distributed orchestration and broader administrator-phone transfer are remaining implementation, not disguised as hardware blockers. The complete redesigned experience is not store-ready. The next concrete physical test is a separately authorized independent-lamp bootstrap with the exact default candidate, checking identity and all retained settings. The new progress cue cannot run while the old 1.14 updater installs 1.15: demonstrate on/off receiver-only progress, cancellation and restart only after supported firmware is running, using a separately pinned higher test-version artifact or an explicitly approved same-version repair. Only the 1.15 candidate artifacts listed here have been prepared.
