# Physical acceptance for the unpublished experience candidate

Nothing in this procedure has been executed on a real lamp during this implementation. Obtain separate authorization for the exact artifacts and each physical configuration change first. Keep the existing router, SSIDs, channel/VLAN/isolation and working primary↔IoT arrangement fixed throughout controlled tests. Do not interpret a build, mock radio or successful download as physical acceptance.

## Preparation and recovery baseline

Use the artifacts and SHA-256 in `.build/experience-artifacts.json` after the final build, not an unpinned Latest release. Verify the file digest again immediately before use. Public-format here means the build flavor; it is not publication or production publisher trust. The default candidate has no invented manufacturer/publisher root. A signing-enabled production rehearsal requires an approved public trust JSON, a separately controlled signing key and original signed manifest/image.

For each target record its verified canonical identity, actual port/address, running firmware/hash/slot, bootloader/partition hashes, model/style, count/midpoint/current budget/microphone, startup mode/brightness, all individual colors/options/palettes, ownership/bonds, Wi-Fi and group order/paused membership, automatic update policy and current optical state. Do not log passwords, fleet keys, phone invitation secrets, raw microphone data or production private signing material. Take a recoverable backup before an approved install/fault experiment. Confirm two 0x1F0000 OTA application slots on the actual lamp; the compile-time layout alone does not prove the installed layout.

Install a separately approved candidate on one independent canary first. Confirm exact identity/version and a fresh authenticated control response after restart, then compare preserved settings with the baseline. Existing application-only USB service avoids rewriting partitions/NVS, but the exact port/slot/image must be verified before separately authorizing it. A mismatched or legacy layout requires a deliberate backup-protected service migration, not ordinary OTA.

The default unpublished 1.15.0 application is 2,019,760 bytes, SHA-256 `ca83d570010b8022c41d404a717a95295699020df5e83bd41cb90f1a6dcc96d4`, with its matching manifest under `.build/experience-candidate-public`. The separate four-root development budget build is not for installation. Do not use the merged service image as an OTA image. The new updater cue executes in the currently running firmware: a legacy 1.14 receiver installing 1.15 cannot display it. Once the candidate is running, the full cue test requires a separately pinned higher test-version artifact or a separately approved same-version repair; no such additional release artifact is represented as prepared here.

## One-lamp control and native setup

1. On a real supported iPhone and Android, test native permission denial, permission recovery, accessory authorization, existing bonds, one active BLE connection and three-bond capacity. Open pairing with the six-second blue recovery gesture; release on blue. Verify three-second hotspot and deliberate ten-second reset separately only on the approved reset fixture.
2. Verify unknown/future model IDs retain identity with generic artwork; preconfigured production units must not request LED engineering values. Test current Helix, Large helix and Corkscrew without inferring calibration from style.
3. Read that lamp's own catalog v1/v2. Check all legacy names/order, solids without motion, automatic/custom spectrum, VU zones, Fountain bands, Prism fixed rainbow and safe unknown-effect controls. Test 1, odd and maximum LED configurations only within approved real power/hardware limits; host geometry coverage is not power/thermal proof.
4. Tune an effect, durably save appearance, restart and confirm tuning while the independently chosen startup mode/brightness stay unchanged. Inject failed saves/power cuts on the fault fixture; report accepted versus persisted exactly. Run knob/second-phone changes while a draft is open; stale CAS must reject without overwriting either change.
5. Lose a post-execution reply. Query the original target/boot/command over a different authorized route. Confirm no mutation replay, honest expiry/reboot uncertainty and fresh target state before releasing the lane. Probe twenty saved lamp cards with bounded concurrency; unavailable lamps must not stall unrelated controls or native navigation.

## Newcomer and household identity

1. Keep an existing fleet/network/group/bonded lamp unchanged and verify it never advertises as factory-new merely because a storage read failed. Exercise wrong target, boot, fleet, transcript, canceled/expired request and lost final confirmation.
2. Use an unowned candidate through an existing protected broker. Select comparison v2 only when the app presents the entire six-symbol plus check-symbol comparison. Compare redundant color/pulse cues on the real diffuser; approve only with the target's physical click after a full cue cycle. A remote Yes button cannot approve. Test visual/color impairments and a validated assisted alternative with actual novice older participants. Automatic first-phone setup still needs a phone-side authenticated transcript or genuine manufacturer identity prerequisite.
3. Grant a second phone limited light control through confidential bonded BLE, directly or through new protected mesh bridges. Transfer the grant through an authenticated confidential native exchange, store it in the native vault and require a signed fresh target state before creating an owned card. Plain HTTP invite/result retrieval must fail. A forged HTTP 200/body/tag must never become success.
4. Revoke that phone on each reachable lamp; verify prior proofs fail after reboot. Keep unreachable members explicitly pending and reconcile them later. Test lost phone/vault, invitation expiry, capacity and readback/storage failures. Household light grants do not revoke native administrator bonds or shared fleet/access-password authority. Ownership transfer uses the deliberately approved physical reset/reprovisioning path; compare preserved physical model/hardware/trust and cleared user authority afterward.

## RF, group scale and complete dissolution

First prove genuine three-node control forwarding by preventing direct origin-to-target overlap while retaining two adjacent links; record exact target response/boot, not delivery ACK counters. Use existing channels and controlled placement or shielding, never silently modify router settings. Prove Bluetooth→Wi-Fi and Bluetooth→trusted bridge handoff with identity checks and uncertain mutations. Channel incompatibility/no bridge must remain an honest unavailable route.

Create one negotiated v3 group with **20 actual lamps**, then exercise the 32-position address space if a fixture exists. Verify every member's protocol/capabilities before joining. Include mixed physical styles, one microphone coordinator and followers without microphones. Preserve missing/offline positions; a paused follower retains membership and its local appearance and does not resume because of a group command. Run Mirror and all spatial/audio scenes. Unsupported legacy members must receive explicit incompatibility; preserve an independent nine-position legacy group separately.

Measure with synchronized video/photodiodes and timestamped command/telemetry captures. Suggested release thresholds, to be confirmed with product owners, are:

| Measurement | Proposed pass threshold |
| --- | --- |
| Direct/group control latency | p95 ≤250 ms; no target exceeds 1 s while reachable |
| Spatial synchronization skew | p95 ≤35 ms, worst ≤75 ms across the 20 lamps |
| Sustained stream availability | ≥99.9% measured frames/windows across a 2-hour run; no unexplained fallback |
| Recovery after coordinator/channel overlap returns | Fresh nonce admission and correct order within 10 s, with stale frames rejected |
| Free/largest heap during control, audio and updates | Record worst values; largest block must exceed the largest required allocation plus 25% margin |
| Loop/update task stack | Record minimum high-water marks; ≥1024 bytes remaining on each tested critical task |
| Knob/render responsiveness | No watchdogs; p95 knob response ≤100 ms; measured frame/update cadence remains within declared bounds |

These are acceptance targets, not measured results. Repeat under Wi-Fi traffic, BLE control, audio, periodic presence, loss/duplication/reordering, MCU/time rollover fixtures and finished enclosure placement. Measure supply current, thermals and RF range separately within real hardware ratings.

Test direct dissolution of a two-lamp and a large group: verified followers leave first, durable coordinator order prunes only confirmed departures, then coordinator stops last. Individual settings must match the baseline. With one follower unreachable, retain its position and show `pendingRemovalIds`; never hide the group or demote the coordinator early. Removal of one/last follower must bypass the two-member creation rule. Move the last follower into another group; confirm source cleanup on success and after a failed destination join. A lamp that left but failed to join stays visibly independent, and an unreachable source coordinator stays pending. Lose replies at every leave/prune/demotion boundary and reconcile fresh identities/sessions before continuing.

## Updates, progress cue and staged rollout

1. Verify default automatic opt-out, explicit persistent opt-in, unknown clock/DST/window/defer behavior and manual Update now. A donor obeys the receiver's policy. Arm every v3 member durably before a staged rollout; do not claim a global hold from one coordinator ACK. Freeze one exact artifact, reserve one member, verify postboot health before advancing, and update the coordinator last. Lost lease/health/release replies require the original durable ticket/proof reconciliation. There is no autonomous radio ticket-distribution claim.
2. Test reliable lamp-direct HTTPS, separate trusted signed donation and authorized direct BLE with a phone-verified exact package. Keep generic mesh uploads prohibited. A malicious same-fleet donor's altered publisher metadata or image must fail before boot selection. Test wrong chip/version/size/hash/signature/epoch, missing original donor metadata, opted-out receiver and donor resource ownership.
3. Interrupt BLE prefix/data/ACK/final ACK, lock/background/terminate iOS and Android, disconnect and reconnect. An opted-in RAM lease resumes only the same target/artifact/session within 120 seconds at negotiated MTU; power cycle/expiry/Cancel/different image cannot resume. After possible Finish, read installed version/identity/control health rather than repeating commit. No fabricated ETA or unattended phone promise.
4. Confirm the new status animation is visible **only on the receiver while its update operation is active**, and absent from both effect catalogs. Begin with the receiver on: a subtle warm animation and growing folded-height progress band should reflect confirmed written bytes. Begin with it off: it must remain dark for the entire operation, even if a test changes the later power state. Capture brightness at admission and preserve power/mode/appearance. Donor and other group lamps must never display the update cue. Release checks/postboot health alone must not display it. Unknown-total legacy upload shows gentle indeterminate motion without a fabricated percentage. Measure cue cadence, actual progress correlation, radio throughput and current budget.
5. On an approved sacrificial fixture, install a valid but deliberately unhealthy image and verify the actual installed bootloader performs bounded rollback before confirmation. The pinned SDK enables rollback, but this does not prove the installed bootloader. Check settings retention, loop continuity, restart selection and prevention of update loops. Stop and use the explicit recovery/service path if prerequisites are absent.
6. Before the first candidate on a legacy image without attempt-quarantine support, separately authorize automatic opt-out and a verified bootstrap. On supported firmware, interrupt after durable attempt insertion and before/during boot selection; the exact unconfirmed artifact must not automatically reinstall after restart/rollback. Verify an explicit approved repair can proceed, and only continuous health plus the measured exact installed artifact clears its entry. Failed health clears retry at most once per minute; full/corrupt storage stays blocked for the deliberate service route and retains other trust/settings. A pending entry alone must never be presented as proof that the bootloader rolled back.

Retain per-target results and exact digests. Advance from canary to one follower, then staged group, then twenty-lamp load only after each gate passes. No public release or store-readiness claim follows automatically from this procedure.
